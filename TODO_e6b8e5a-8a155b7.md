# Code Review: e6b8e5a-8a155b7

## Commits reviewed

- `e6b8e5a` — `feat(auth): implement device-code flow with 2FA and keyring session` — Device-code OAuth against `/identity` (start + single-poll + 2FA + silent refresh), keyring refresh-token storage, `last_user_id`/`device_identifier` in config, `Task`-based polling loop, login/2FA views. - `8a155b7` — `feat(cache): add encrypted SQLite vault snapshot` — AES-256-GCM blob encryption, SQLite `cache.db` (WAL) keyed by SHA-256(user_id), self-healing `Cache::{save_vault,load_vault,discard}`, `CacheKey { key, salt }` from the PIN, unlock-loads/logout-discards wiring. Plan Step 7.

## Summary

Both commits deliver their plan steps faithfully: the device-code flow matches the RFC 8628 two-endpoint correction recorded in the plan, the cache matches the AGENTS.md cache design (SHA-256 row id, fresh 96-bit nonce per write, self-healing `None` on wrong-key rows, WAL), and both commit messages follow the `type(scope): summary` + Why/What/Validation format with one commit per step. Literate-programming compliance is high — every touched file opens with a narrative preamble before imports, concerns are named in one sentence, and doc comments explain reasoning rather than signatures. Test quality is good (65 pass; reducer tests are XDG-isolated; encryption has round-trip/wrong-key/tamper/fresh-nonce coverage), though several live behaviors are untested (slow_down backoff, boot restore path, WAL, `now_epoch_secs`) and wiremock tests rarely assert request shape. The most important gaps are runtime protocol/correctness issues that mock tests cannot catch: a dead-end UI state when a poll fails mid-flow, a non-sticky RFC 8628 `slow_down` backoff, likely-wrong 2FA form-field names against real Bitwarden/Vaultwarden servers, and plaintext PIN/TOTP/decrypted-vault exposure through `State`'s derived `Debug`.

## Findings

1. **major** — `src/app.rs:175-179` (`Message::AuthFailed`) + `src/ui/login.rs:51-59` — When a poll fails mid-flow (network error, unmappped `invalid_grant`, 5xx), `auth_error` is set but `device_code` is kept and the screen stays `DeviceCode`, where the only buttons are "Open browser" and "Waiting for approval…"; the "Log in with device" restart button renders only when `device_code` is `None`, so the user is stuck until they restart the app. Suggested fix: on `AuthFailed` while `screen == DeviceCode`, clear `state.device_code` (or add a "Try again" message) so the start button reappears.
2. **major** — `src/app.rs:235-240` (`handle_poll`, `SlowDown`) — RFC 8628 §3.5 requires the interval to increase by 5 s **for all subsequent requests** after `slow_down`, but the backoff is applied to a single wait: the next `Pending` outcome re-reads the unchanged `device_code.interval` (`poll_interval`, app.rs:383-390) and polls at the original cadence, risking the server's client lockout. Suggested fix: track an accumulated backoff offset in `State` (reset on `DeviceCodeReceived`/`fail_login`) and add it in `poll_interval`.
3. **major** — `src/state.rs:27-54` — `State` derives `Debug` while `pin_input`, `pin_confirm`, `two_factor_input`, and `cached_vault` (the decrypted vault JSON) are plain `String`s, so any `{:?}`/tracing of `State` prints the plaintext PIN, the live TOTP code, and the whole decrypted snapshot; the module comment claims Debug masking "cannot leak tokens" but covers only `Session`. Suggested fix: hand-write `Debug` for `State` (or wrap the sensitive fields in masked/`Zeroizing` newtypes) and add a test like `auth_tokens_debug_is_masked`.
4. **major** — `src/api/auth.rs:222-224` (`poll_device_code` 2FA resubmit) — The second factor is sent as `two_factor_token` and no provider is selected; official Bitwarden clients send camelCase `twoFactorToken` plus `twoFactorProvider`, and ASP.NET-style form binding on Bitwarden/Vaultwarden will not match the underscore name, so real servers likely keep returning `TwoFactorProviders` and the UI loops on the 2FA screen. The wiremock test (auth.rs:524-543) asserts the client's own output, so it cannot catch this. Suggested fix: verify against a live server at first manual run (as AGENTS.md already mandates for the endpoint path) and match the official client's field names/casing; note the gap in AGENTS.md's "Device-code 2FA response shapes" gotcha.
5. **minor** — `AGENTS.md:131` (State Machine) vs `src/app.rs:300-327` (`logout`) — AGENTS.md says "Logout -> wipe keyring/cache/PIN verifier" but the code never clears `config.pin_verifier`; plan Step 6c only promises "keyring + session" (cache was added in Step 7). Decide whether logout keeps the PIN (likely — wiping it forces PIN re-setup), then align AGENTS.md with the code.
6. **minor** — `src/app.rs:257-271` (`complete_login`) — If the JWT `sub` extraction fails, the refresh token is silently not stored, `last_user_id` is not persisted, all future cache loads no-op, and logout cannot discard the cache row — with no log line. Suggested fix: `tracing::warn!` when `session.user_id` is `None` so the degraded session is diagnosable.
7. **minor** — `src/app.rs:300-327` (`logout`) — Cache and keyring cleanup are nested under `if let Some(user_id) = state.config.last_user_id` (lost if a prior config save failed, orphaning the snapshot and keyring entry), and `state.pin_error` is never cleared, so a stale "Incorrect PIN" resurfaces on the next unlock after re-login. Suggested fix: key cleanup off `session.user_id` as a fallback, and reset `pin_error` (plus PIN fields) in `logout`.
8. **minor** — `src/app.rs:262`, `:305-312`, `:334`, `:440` — Keyring (`set_password`/`delete_credential`/`get_password`), SQLite open + WAL, and config writes all run synchronously on the update/UI thread; Secret Service over D-Bus can stall for seconds and pin the event loop. The plan's Task-based design covers network auth only. Suggested fix: move keyring/cache I/O into `Task::perform` futures like the HTTP steps (at least `complete_login`/`restore_session`).
9. **minor** — `src/api/auth.rs:386-543` (wiremock tests) — Only 2 of 9 mock tests assert request shape (`body_string_contains` for the 2FA token and refresh grant); the core device-grant poll never asserts `grant_type=urn:ietf:params:oauth:grant-type:device_code`, `device_code`, or `client_id`, and `start_device_code` never asserts `client_id`/`scope`/`deviceIdentifier`. Suggested fix: add request-body matchers to the happy-path start/poll tests, which is exactly what would have caught finding 4's field-name drift.
10. **minor** — `src/message.rs:16` and `:28` — The `#[allow(dead_code)]` on `Screen` is obsolete (all six variants are constructed in non-test code, per AGENTS.md's allow-triage step), and the `Message` allow comment names "Logout/Noop" although `Noop` is constructed in `app.rs:164`; only `Logout` still awaits a view. Suggested fix: drop the `Screen` allow and tighten the `Message` comment to `Logout`.
11. **minor** — `src/cache/mod.rs:89-103` (`load_vault`) — A decrypt that succeeds but yields non-UTF-8 bytes returns `Err(CacheError::InvalidSnapshot)` without deleting the row, contradicting the module preamble's "unreadable rows are deleted and reported as None" contract; `unlock_cache` just warns and the corrupt row is retried forever. Suggested fix: treat `InvalidSnapshot` like a decrypt failure (delete + `Ok(None)`).
12. **minor** — `src/app.rs:717-736`, `:771-790` — The `logout` reducer tests reach the real OS keyring: `logout` calls `auth::clear_refresh_token("user-7"/"user-9")`, which executes `delete_credential` against the actual Secret Service, so a dev machine with a genuine `vaultmaid/refresh:user-7` entry gets it wiped by `cargo test`. Keyring I/O is not headless-testable, but a seam is feasible: inject a keyring trait / `keyring::set_default_credential_builder` mock so logout reducers are hermetic.
13. **minor** — `src/app.rs:166` + `:346-352` — There is no generation/epoch guard on async auth results: a slow boot-time `silent_refresh` that resolves after the user has already completed a fresh device-code login overwrites `state.session` and jumps the screen back to `Unlock`/`SetPin` (`complete_login`). Suggested fix: tag auth tasks with a flow id in `State` and ignore stale `SessionRestored`/`PollFinished` results.
14. **minor** — `src/app.rs:235-240` (`SlowDown`), `:329-353` (`restore_session`), `src/cache/mod.rs:127-133` (`now_epoch_secs`), `src/cache/storage.rs:56-59` — Untested behaviors: the +5 s backoff schedule, the boot silent-refresh branch (keyring hit/miss), `now_epoch_secs` (including the pre-epoch `"0"` fallback), and WAL on a file-backed database (all storage tests use `open_in_memory`, where `PRAGMA journal_mode=WAL` is a no-op). The tests exist or are cheap to add for everything except WAL; a file-based storage test would also exercise it.
15. **minor** — `src/api/auth.rs:77-84` (`DeviceCode`) — `DeviceCode` derives full `Debug` (exposing `device_code`, a credential per RFC 8628 §5.4 that can be exchanged for tokens once the user approves) and is embedded in the `Debug`-derived `State`; `AuthTokens`/`Session` got masked Debug for exactly this reason. Suggested fix: mask `device_code` in a hand-written `Debug` impl.
16. **minor** — `src/app.rs:719` vs AGENTS.md verification discipline — `cargo clippy -- -D warnings` (the documented command) passes, but `cargo clippy --all-targets -- -D warnings` fails with `clippy::field_reassign_with_default` in `logout_clears_session_material` (app.rs:719-723), so the linter never sees test code under the current workflow. Suggested fix: fix the struct literal, and consider making `--all-targets` the documented invocation.
17. **nit** — commit message of `e6b8e5a` — Claims "12 wiremock auth tests … 401/expired", but the module has 9 wiremock tests (12 total), and no test exercises the `401` arm of `silent_refresh` (only 400). Suggested fix: either add the 401 test or correct the count in future messages.
18. **nit** — `src/app.rs:371-380` (`device_info`) — `std::env::var("HOSTNAME")` is unset outside login shells on many Linux sessions, silently degrading to `"vaultmaid"`, and `device_identifier.clone().unwrap_or_default()` would send an empty id if boot's config save had failed. Cosmetic-only (server treats the name as cosmetic); consider `hostname`-crate lookup or at least logging the fallback.
19. **nit** — `src/ui/login.rs:19` and `src/api/auth.rs:316-330` — Literate-contract polish: `error_text` is defined before the functions that call it (contract red flag "helpers before code that calls them"), and the `save_refresh_token`/`load_refresh_token` docs restate the signature ("Store the refresh token for `user_id` in the OS keyring") without reasoning. Suggested fix: move the helper below its callers and give the token helpers docs that carry the missing-entry/privacy rationale instead.
20. **nit** — `src/api/auth.rs:308-311` (`user_id_from_token`) — The `STANDARD_NO_PAD` fallback silently accepts non-JWT base64 payloads for a field that per its own doc is always a JWT middle segment; harmless, but the extra alphabet widens accepted input for no benefit. Suggested fix: drop the fallback or document a concrete response shape that needs it.
21. **nit** — `src/api/auth.rs:77` — `DeviceCode` derives `Serialize` but is only ever deserialized (state is never serialized); drop the derive or justify it for the planned sync payload. `CacheKey`'s `pub` fields (src/pin.rs:143-147) also allow arbitrary mutation of the key after derivation; a read-only accessor would preserve the invariant that only `derive_cache_key` mints keys.
22. **nit** — `plans/1787254773478-vaultmaid-implementation-plan.md:256` — Recorded correction ends with a double period ("adjust there only.."). Cosmetic.

### Verified clean

- **SQL**: every statement in `storage.rs` uses `params!`/`?N` placeholders; the user-derived `cache_id` is never interpolated into SQL.
- **Nonce handling**: `encryption.rs` draws a fresh 96-bit nonce from `OsRng` per write, stores it alongside the ciphertext (correct GCM practice), returns an explicit error on width mismatch, and has a freshness test; the blob-level rationale in the preamble matches AGENTS.md.
- **Key/salt handling**: the AES key is never written to disk (`salt` column records only the Argon2 salt string); `Pin` is `Zeroizing`, `CacheKey`/`AuthTokens`/`Session`/`Pin` have masked `Debug` impls with tests; config holds only the Argon2 PHC verifier.
- **JWT `sub` without verification**: justification is sound — the token comes from the server just dialed over TLS and is used only as a keyring/cache namespace, never as an authorization decision; reasoning is documented at the function.
- **Keyring usage**: service `vaultmaid`, account `refresh:{user_id}`, `NoEntry` treated as absent on load and delete — matches AGENTS.md exactly; secrets never reach config TOML.
- **No panics**: every `unwrap`/`expect` in the codebase is under `#[cfg(test)]`; error paths return `Result`/`Option` throughout.
- **Config compatibility**: `#[serde(default)]` on the new fields plus the legacy-config test confirm old `config.toml` files load unchanged; the save/`save_to` split matches the recorded decision.
- **Self-heal**: wrong-key/corrupt rows are deleted and reported as `None` with a test proving the correct key then finds nothing (one UTF-8 edge case excepted, finding 11).
- **Commit discipline**: one commit per plan step, `type(scope): summary` format with Why/What/Validation bodies, and the RFC 8628 endpoint correction is recorded in both the plan and AGENTS.md ("Device-code endpoints" section) consistently with the code constants.
